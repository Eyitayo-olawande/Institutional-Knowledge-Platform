# CLAUDE.md

Rules every Claude Code session in this repository follows. They come from Product Architecture v1 and Development Roadmap v1. Significant changes to these rules are made through a decision record in [docs/adr](docs/adr/README.md).

## Architecture rules

* One codebase, never forked. Customer differences live in settings, templates and packs, never in custom code.
* Database per tenant. Every request is mapped to exactly one tenant from its domain before any data is read.
* No personal data in the control database. It holds only tenant records, plans, hosting location and pack subscriptions.
* Configuration over code. Departments, role levels, wording, certificate rules, pass marks, evidence packs and regulator content are data.
* People approve, the platform assists. Any automated help produces drafts that a named person approves.

## Engineering rules

* Every data access goes through the tenant context; direct database connections elsewhere are blocked by a lint rule.
* No personal data in the control database, logs or usage events.
* Every change that alters data writes to the activity log.
* No screen text typed into code; all text comes from translation files through `t()` (apps/*/messages/<locale>.json; a lint rule blocks text typed into JSX).
* Every structural word comes from the tenant's wording labels.
* New behaviour arrives with tests; bug fixes arrive with a test that fails before the fix.
* Migrations are safe on a live system and run against every tenant database in tests.
* Unfinished features hide behind per tenant feature switches.
* One work package per branch and pull request, with a summary a non developer can read.
* Significant choices are recorded as a decision record before code depends on them.

## Rules for every table

A creation and change timestamp, the person who made the change, soft deletion where retention rules require history, and no personal data in the control database or usage tracking.

## Build loop for every work package

1. **Define.** The product owner writes or approves the work package: goal, acceptance criteria, screens or rules, link to the blueprint.
2. **Plan.** Claude Code reads this file, the design documents and existing code, then proposes a short plan. The technical lead approves or corrects it.
3. **Build.** Claude Code writes code, tests and any migration, runs the full suite and opens a pull request with a plain summary.
4. **Check.** Tests, type checks, linting, tenant isolation tests, dependency scanning, code review and security review.
5. **Review.** The technical lead reviews and merges.
6. **Accept.** The product owner checks the feature on staging against the acceptance criteria.

Work packages that touch the same area run one after another to avoid conflicts. Shared modules (tenancy, permissions, activity log, notifications) are built first and used by everything after.

## Definition of done

Acceptance criteria met on staging; tests written and passing; no tenant isolation or security check failures; translation keys used for all text; activity log entries where data changes; reviewed and merged by the technical lead; accepted by the product owner.

## Data and access

Claude Code works in development and staging only and never holds production credentials or SUNU personal data. Tests and demos use a fictional insurer generated by script.

## Commands

Node 20 or newer and npm workspaces (apps/* and packages/*).

* `npm install`: install dependencies for every workspace
* `npm run lint`: ESLint, including the rule that blocks database drivers outside packages/db
* `npm run typecheck`: TypeScript in strict mode
* `npm run test`: Vitest unit and integration tests
* `npm run check`: all three, in that order; run before opening a pull request
* `npm run build`: production build of every app
* `npm run db:setup`: create the local control and fictional tenant databases (Postgres.app), migrate and seed
* `npm run db:migrate`: apply control database migrations
* `npm run control:generate -w @mantle/db`: generate a migration after changing packages/db/src/control/schema.ts; review the SQL before committing
* `npm run dev -w @mantle/web` (port 3000), `npm run dev -w @mantle/console` (port 3001), `npm run dev -w @mantle/worker`: run one app locally

GitHub Actions runs the same checks, plus `npm audit` for high or critical vulnerabilities, on every pull request and every push to main (.github/workflows/ci.yml). Dependabot opens weekly update pull requests.
